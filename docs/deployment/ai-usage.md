# 会员、训练积分与 AI 额度

当前是开发阶段的额度控制基础，未接入支付，也没有正式售价。官方服务与自部署实例各自维护账号、会员、额度和模型配置；客户端不包含模型密钥。

## 三种独立状态

| 状态 | 用途 | 获取方式 |
| --- | --- | --- |
| 训练积分 | 外观兑换与训练奖励 | 注册、签到、对弈、做题或管理员调整 |
| 会员 | 决定当前月度额度采用免费还是 Pro 上限 | 管理员开通、续期或取消；尚无在线支付 |
| AI 额度 | 控制实际模型调用 | 自然月额度与管理员发放的补充额度 |

训练积分不再兑换 AI，旧余额与流水原样保留。Pro 的 AI 使用也有上限；管理员进行训练、讲解和复盘时同样使用 Pro 额度。规则讲解、基础训练和本地引擎不消耗 AI 额度；本批不对普通引擎 API 增加新的计费规则。

## 默认测试策略

- 免费账号：每自然月 20 单位。
- Pro / 管理员：每自然月 600 单位。
- 教练计划 20、整局报告 10、单步失误讲解 2、题目讲解 8、走法点评 4 单位 / 次。
- 优先扣月度额度，不足部分使用补充额度。月度余额不结转，补充额度不因跨月而失效。
- 同一月份内开通、续期或取消会员不清零已用量。降级后若已用量超过免费上限，该月可用月度额度为 0，仍可使用补充额度。

月份与重置时刻按部署的 `TZ` 定义，默认 `Asia/Shanghai`。请求预留后即占用额度，页面“已用”包含尚未完成的预留。调整月度上限不会重置已用量，修改动作单价只影响之后新建的请求。

一次整局复盘可能生成多处失误讲解、整局报告和教练计划，分别计量；不足时保留引擎分析和基础训练安排。命中题目已有讲解缓存不重复扣额度；模型未启用时不预留额度。

这些数字用于验证行为，不是正式套餐。接支付前还需确定订阅账期、月底开通是否按比例发放、模型成本与超额包价格；当前自然月策略可能让跨月开通者在短期内获得两个月的额度，不应直接作为正式收费承诺。

## 用户与管理员如何使用

用户在“设置 → 账户与 AI 额度”查看当前服务器的月度上限、剩余额度、补充额度和最近调用记录。训练积分单独展示；生成失败的记录显示“已退回”。

Web 管理后台新增“AI 额度”页：

1. 修改免费 / Pro 月度上限及各项动作消耗，保存后对后续请求生效。
2. 选择用户，为其增加或扣回补充额度，必须填写原因；扣回不会形成负余额。
3. 查看本月模型调用数、失败数、token 总量、已知单价部分的估算费用与未知费用调用数。
4. 服务异常重启后，可为用户回收超过 15 分钟未完成的预留。

正常 AI 请求也会在再次预留前自动回收该用户的过期预留。回收后到达的旧结果不会再次结算或转为成功，避免重复退款。运维用的后台模型连通测试独立记录成本并限流，不扣个人训练额度。

## 部署配置

后端环境变量（`backend/.env` 或运行环境）：

| 变量 | 默认值 |
| --- | --- |
| `AI_FREE_MONTHLY_UNITS` | `20` |
| `AI_PRO_MONTHLY_UNITS` | `600` |
| `AI_COST_COACH_PLAN` | `20` |
| `AI_COST_GAME_REPORT` | `10` |
| `AI_COST_MISTAKE_EXPLAIN` | `2` |
| `AI_COST_PUZZLE_EXPLAIN` | `8` |
| `AI_COST_PLAY_COACH` | `4` |

Docker Compose 根目录 `.env` 支持同名变量。管理后台保存的数据库策略优先于环境变量；改环境变量不会覆盖已在后台保存的值。月度上限允许为 0，动作消耗必须是正整数，均不超过 1,000,000。非法配置回退到内置默认值，不会意外放行无限调用。

本机引擎与 AI 额度均属于所连接实例的独立能力。自部署者可自行配置额度和模型密钥；该实例不会向官网购买额度，也不会继承官网会员。

## 扣减与退款规则

`ai_quota_accounts` 保存补充余额及每用户写锁，`ai_quota_months` 保存月度用量，`ai_operations` 保存动作、请求标识、原始单价和两类额度分摊。`ai_quota_adjustments` 保存管理员补充额度调整。

每次调用分成三个阶段：

1. 在短事务内锁定账户、检查剩余额度、预留单位并提交。
2. 释放数据库锁后调用模型，记录供应商返回的 token 与费用估算。
3. 成功保存结果并标记完成；异常或空正文按该请求原始分摊退回，即使单价、会员或月份已经变化。

相同用户与请求标识具有唯一约束。处理中返回 pending / HTTP 409（视业务接口而定），成功重试复用保存结果；退款、管理员调整和超时回收均不会重复入账。SQLite 使用写事务串行化，PostgreSQL 使用账户行锁，不依赖单进程的内存锁。

客户端为 POST 请求生成 `Idempotency-Key`。自定义调用方在重试同一次逻辑请求时必须复用该标识；真正重新生成时使用新标识。标识限制为 1–80 个字母、数字或 `_ . : -`。复用到不同动作或关联对象会冲突。管理员补充额度表单在失败重试时保留原标识，成功或修改表单后才更换。

成功请求的文本会保存在账本，便于响应丢失后的重试复用；删除账号时清理其额度与结果，并匿名化已有成本日志。业务缓存保存失败后可用同一标识重试写入结果，不再发起模型调用。账本数据库不可用时不会继续放行模型调用；数据库异常造成的未结算预留可在 15 分钟后回收。

## 成本记录与局限

`llm_call_logs` 保存每次实际模型调用的动作、用户、模型、token、耗时、成败及关联的 `operation_id`。`cost_known=false` 表示缺少已维护的单价或使用量，不代表免费；旧成本记录默认归为未知。当前价格表只是估算，不能替代供应商账单。

模型返回空正文时，用户额度会退回，但供应商可能已消耗 token，这笔成本仍会记录。额度结算与成本日志分开：额度账本失败会阻断调用或等待恢复；供应商成本日志采用尽力记录，写入失败会记服务日志，管理员需结合供应商账单核对。

尚未实现支付订单、支付回调、退款支付、正式超额包售卖、供应商账单导入或系统级任务队列。不要把手工发放补充额度当作已完成支付集成。

## 升级与验证

本批新增 Alembic revision `202610290004`。升级前备份数据库，再启动新后端自动执行迁移；旧积分不转换成 AI 余额，既有会员有效期不变。应同时更新客户端，避免旧界面继续显示“积分兑换 AI”或“Pro 不限次”。回滚涉及删除新账本表，需配套备份，不能仅回退代码。

常规验证：

```bash
cd backend
uv run pytest tests/ -q
uv run alembic upgrade head
uv run alembic check
```

可选 PostgreSQL 集成测试使用 `XIANGQIDAO_TEST_POSTGRES_URL` 提供测试连接，需有创建 schema 权限。测试只创建并清理自己的随机 schema，验证迁移、并发预算与请求幂等，不修改既有表：

```bash
uv run pytest tests/test_ai_usage.py -q
```

生产部署与备份参见[后端部署文档](backend.md)。
